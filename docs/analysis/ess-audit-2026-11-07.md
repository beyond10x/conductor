# The specification on ESS 0.90: audit and hardening, 2026-11-07

The specification moved from `ess 0.60` to `ess 0.90` (`spec/ess-inputs.yaml`, `b10x.toml`, the
`ESS_VERSION` of `.github/workflows/check.yml`), and `crates/conductor-model` was regenerated with
`ess 0.90.0`. The new generator adds a `broken_constraint` check to every `String` newtype with an
`alphabet:`, `prefix:` or invariant, and drops the model digest from the headers; it refuses
nothing in `spec/` and changes no handler. Then the specification was audited for soundness and
gaps, and hardened with the techniques of the `ess:hardening` skill that fit here.

Instruments: `ess specify validate --path spec --format json` (its `completeness` block),
`ess verify conform synthesize`, `ess verify conform run --target interpreted`,
`ess verify conform mutate --target interpreted`, `ess verify diff --compatibility`,
`ess specify compile --format json` (the IR), `crates/conductor/tests/cli_tree.rs`, and a read of
the handlers in `crates/conductor/src`.

`ess specify validate --path spec` exits 0 with no warning once `requires:` names 0.90 (on 0.60 it
warned that the pin is older than the binary). Its `completeness` block, before and after the
fixes of § 5:

## 2. Conformance: what runs and what does not

`ess verify conform run --path spec --scenarios spec/scenarios --target interpreted
--report-format 2` (the `task check` step, Taskfile.yml:322), on ess 0.90.0:

| measure | count |
|---|---|
| scenarios run | 409: 378 synthesized and 31 authored, the conformance step taking every file of `spec/scenarios/` (the 2 unlisted and the 3 of § 5 included) |
| passed / failed / error | 409 / 0 / 0 |
| skipped / unsupported | 0 / 0 |
| owed and not synthesized (`unscenarioed`, § 1a) | 18 |
| `conformance_status` | `inconclusive`: the report carries `coverage.knowledge: unknown`, because the run is not given the coverage suite; `execution_status` is `passed` |

**The conformance run holds the specification, not the handlers.** `task check` runs the suite
with `--target interpreted` (Taskfile.yml:322): ESS's reference interpreter of `spec/`. No
`Target` adapter over `conductor` exists, so a green run says the scenarios agree with the model;
the handlers are held by `crates/conductor/tests/` alone. The handlers decide every outcome through
the generated `conductor_model::behaviour` (crates/conductor-model/src/behaviour.rs), so the
decision logic is the specification's; what no conformance run checks is the store, the views'
rows and the records lines the handlers write around it.
